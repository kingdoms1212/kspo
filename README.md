# Hi스포링


### Hi스포링 이름의 의미


**Hi스포링**은 사람(Human)과 인공지능(AI)을 의미하는 HI와 스포츠(Sports)와 연결(Ring)의 의미를 담은 스포링을 결합한 서비스명입니다.


사람의 판단과 인공지능의 데이터 분석을 결합하여 지역 특성에 적합한 체육 프로그램을 제안하고, 지역사회와 스포츠·체육복지를 연결한다는 의미를 담고 있습니다.

## 2. 프로젝트 개요


### 프로젝트 소개


**Hi스포링**은 공공기관 체육복지 담당자가 지역별 체육 이용 현황과 기존 프로그램, 체육시설 등의 공공데이터를 한곳에서 확인하고, 이를 바탕으로 지역에 적합한 체육 프로그램을 설계할 수 있도록 지원하는 **체육복지 정책 의사결정 지원 플랫폼**입니다.


사용자는 지역 현황을 분석한 뒤 종목·시설·운영 정보를 선택하여 신규 체육 프로그램을 설계할 수 있으며, AI는 **제공된 근거 범위에서 지역 현황과 프로그램·시설 적합성을 검토합니다.** 분석 결과는 프로그램 기획의 보완 자료로 활용되며, 최종적으로 **체육 프로그램 운영 계획서 작성까지 하나의 흐름으로 연결**됩니다.


이를 통해 단순한 체육시설 및 프로그램 정보 조회를 넘어, **공공데이터와 AI를 활용해 담당자의 정책적 판단을 지원하고 지역 특성에 맞는 체육복지 프로그램의 기획과 의사결정을 돕는 것**을 목표로 합니다.


![프로그램 설계 대시보드](docs/readme-assets/dashboard.png)

*지역 현황을 확인하고 프로그램 설계를 시작하는 대시보드*

### 프로젝트 필요성 및 배경


지역에 맞는 체육복지를 실현하려면 주민의 체육활동 이용 실적과 기존 프로그램, 활용 가능한 시설을 함께 살펴보고 이를 프로그램 기획에 반영해야 합니다. **스포츠강좌이용권 이용현황 정보, 공공체육시설 프로그램 정보, 전국 공공체육시설 데이터**를 종합적으로 활용하면 지역별 이용 특성과 프로그램 운영 현황, 시설 자원을 연계하여 체육복지 사업을 보다 효율적으로 기획할 수 있습니다.


Hi스포링은 이 세 가지 공공데이터를 **지역·종목·시설을 중심으로 함께 살펴볼 수 있는 기획 환경**을 제공합니다. AI는 제공된 데이터를 바탕으로 지역별 이용 특성을 해석하고, 설계 중인 프로그램의 강점과 위험요인을 분석하여 구체적인 개선 방향을 제안합니다. 이를 통해 담당자가 **데이터에서 기획의 실마리를 찾고 프로그램을 구체화·보완하는 과정을 능동적으로 지원**합니다. 기존 체육시설과 프로그램 자원을 효과적으로 활용하고, 지역 특성에 맞는 새로운 프로그램을 발굴하여 주민의 체육활동 참여 기회를 넓히는 것이 목표입니다.


### 주요 기능 및 서비스 흐름


| 주요 기능 | 역할 |
|---|---|
| 지역 현황 확인 | 지역별 이용 실적과 종목 분포를 조회하여 프로그램 기획을 위한 기초 정보를 제공합니다. |
| 프로그램 설계 | 기존 강좌와 체육시설을 검색·비교하고 종목·시설·운영 정보를 선택하여 프로그램 운영안을 구체화합니다. |
| AI 검토 | 제공된 데이터에서 지역별 이용 특성과 기획 시 고려할 점을 도출하고, 설계 중인 프로그램의 강점·위험요인을 분석하여 구체적인 개선 방향을 제안함으로써 프로그램의 구체화와 보완을 지원합니다. |
| 계획서 완성 | 검토한 내용을 체육 프로그램 운영 계획서로 정리하고 인쇄 및 최근 계획서 복원 기능을 제공합니다. |

### 활용 데이터


| 데이터 | 서비스 활용 |
|---|---|
| 스포츠강좌이용권 이용현황 | 지역·종목별 시설·강좌·신청 실적 집계 및 AI 지역 분석의 통계 근거로 활용 |
| 공공체육시설 프로그램 | 기존 강좌 검색·비교 및 Excel 내보내기 |
| 체육시설 현황 | 시설 조회 및 정상운영 시설 후보 선택 |
| 시설 인접 교통 정보 | 선택 시설과 연결 가능한 인접 대중교통 정보 조회 |


> 공공데이터 중 지역 통계 분석의 주요 근거는 **스포츠강좌이용권 이용현황 데이터**이며, 프로그램 AI 검토 시에는 선택 시설 정보와 사용자가 입력한 프로그램 정보도 함께 활용합니다. 나머지 데이터는 프로그램 설계와 시설·교통 정보 조회를 지원하는 용도로 사용합니다.


### 데이터 활용 원칙


- 확인 가능한 공공데이터의 이용현황·신청 실적을 **지역 수요를 가늠하는 기초 지표**로 활용합니다. 다만 최신 수요나 지역 전체의 잠재 수요를 직접 나타내는 값은 아닙니다.

- **이용 실적이 높은 지역뿐 아니라 이용이 저조하거나 체육서비스가 부족한 지역도 프로그램 설계 대상**으로 고려합니다. 낮은 실적을 수요 부재로 단정하지 않고 참여 기회 확대 관점에서 기획합니다.

- 미제공 값과 실제 관측된 0을 구분하며, 제공되지 않은 인구·예산·수용능력 등의 값을 임의로 추정하지 않습니다.

- 시설 수만으로 지역의 시설 공급 부족이나 프로그램의 성공 가능성을 단정하지 않습니다.

- 서울 범위로 정제한 데이터를 사용하며 외부 최신 원본 데이터를 실시간으로 자동 수집하는 서비스는 아닙니다.

### 3-2. 시스템 아키텍처

Hi스포링은 **Django 백엔드를 중심으로 사용자 화면, CSV 기반 공공데이터, 외부 정책 정보, Gemini AI 분석을 연결하는 구조**로 구성했습니다.

### 3-4. 프로젝트 폴더 구조

기능별 패키지의 역할과 전체 폴더 구조는 다음과 같습니다.

```text
kspo/
├─ main/
│  ├─ main/                      # Django 설정·URL·WSGI/ASGI
│  ├─ app/
│  │  ├─ dashboard/              # 지역 집계·프로그램 설계·후보 선정
│  │  ├─ programs/               # 강좌 검색·비교·Excel
│  │  ├─ facilities/             # 시설 조회·교통 연결
│  │  ├─ planning/               # 계획서 구성·서명·복원
│  │  ├─ ai_review/
│  │  │  ├─ contracts.py         # 공통 요청·응답·공급자 계약
│  │  │  ├─ factory.py           # 공급자 선택
│  │  │  ├─ errors.py            # 공통 오류 코드
│  │  │  ├─ services.py          # 프로그램 검토
│  │  │  ├─ region_service.py    # 지역 분석·파일 캐시
│  │  │  ├─ prompts.py           # 분석 지침
│  │  │  ├─ schemas.py           # 응답 검증·점수 처리
│  │  │  └─ providers/           # Gemini·더미 어댑터
│  │  ├─ common/                # CSV·캐시·내보내기 공통 처리
│  │  ├─ shared/                # 지역 선택 정책
│  │  ├─ runtime/               # 사전 적재·준비 상태·갱신 감시
│  │  ├─ Batch/                 # 지역 CSV 배치
│  │  ├─ policies/              # 정책 목록
│  │  └─ overview/              # 프로젝트 개요
│  ├─ templates/                # Django 템플릿
│  ├─ static/                   # CSS·JS·지도·로컬 라이브러리
│  ├─ .ai-cache/                # 지역 AI 캐시, Git 제외
│  └─ requirements.txt
├─ data/Batch/                  # 서비스 CSV·manifest·로그
├─ docs/                        # 운영·설계 문서와 README 캡처
├─ scripts/                     # 실행·배포 스크립트
├─ image/ · fonts/ · theme/      # 공통 자산
├─ .env.example                 # 환경변수 예시
├─ render.yaml
└─ gunicorn.conf.py
```

## 6. 데이터 구조 및 저장 구조

### 6-1. CSV를 사용하는 이유와 적용 범위

**서울 지역 프로그램 기획에 필요한 데이터만 정제해 CSV와 메모리 캐시로 제공합니다.** 현재 범위에서 전국 원본 전체를 반복 적재·색인하는 비용과 별도 업무 DB 운영 부담을 줄이기 위한 선택입니다.

- **제공 방식:** 선정 데이터 중 `서울올림픽기념국민체육진흥공단_공공체육시설 상세 정보_GW`만 API로 접근할 수 있고, 나머지 데이터는 API 접근이 불가능하여 전체 데이터 처리 구조를 CSV 기반으로 기획했습니다.
- **서비스 범위:** 현재 기획 대상은 서울입니다. 배치에서 전국 원본을 읽어 서울 행만 추출하고, 서비스는 서울 데이터만 메모리에 적재합니다.
- **확장 방향:** 전국 서비스 전환 시 DB 저장·색인 구조로 확대할 계획입니다. 현재 CSV 선택과 서울 필터링은 각각 저장 방식과 처리 범위에 대한 결정입니다.

### 6-2. 데이터 갱신 및 정제 흐름

**매월 1일 01:00 (Asia/Seoul)에 원본 변경 여부를 점검하고, 변경된 원본을 서울 서비스 데이터에 반영합니다.** 매월 최신 데이터를 기준으로 서비스를 운영하기 위해 월 단위 갱신 주기를 적용하였으며, 매월 1일을 데이터 최신화 기준일로 설정하였습니다. 실행 시간인 01시는 사용자 접속이 비교적 적을 것으로 예상되는 시간대로 임의 산정하였으며, 실제 서비스 운영 환경에 따라 추후 변경할 수 있습니다. 또한 해당 시간은 제공기관의 데이터 갱신 시각을 의미하지 않습니다.

![데이터 갱신 및 정제 흐름](docs/readme-assets/data-refresh-flow.png)

[이미지 크게 보기](docs/readme-assets/data-refresh-flow.png) · [SVG 원본](docs/readme-assets/data-refresh-flow.svg)

**원본 확보와 서비스 반영은 별개입니다.** 원본 CSV를 갱신할 수 있는 API가 없어 현재 배치는 외부의 최신 자료를 자동 다운로드하지 않습니다. 운영자가 새 원본을 반영해야 서비스 데이터도 최신 자료로 바뀝니다. 월간 실행 자체가 원본의 최신성을 보장하지 않으며, 기관별 실제 갱신일·주기가 확인되면 그 일정에 맞춰 조정할 대상입니다.

| 상황 | 현재 처리 |
|---|---|
| 원본 변경 없음 | 원본 버전과 서비스 파일 상태가 같으면 재정제·세대 갱신을 생략하고 `원본 변경 없음`을 기록합니다. 수정시각만으로 판단하지는 않습니다. |
| 원본 변경 또는 서비스 파일 누락 | 서울 데이터를 추출·검증하고 서비스 CSV와 `batch_manifest.json`을 발행합니다. |
| 수동 최신화 | 원본 변경 여부와 무관하게 강제 재정제합니다. 실패 원인과 실행 결과를 다이얼로그에서 확인합니다. |

변경 감지는 로컬에서 **파일 크기·수정시각**, Render에서 **배포 커밋·파일 크기**를 사용하며, manifest의 지역·서비스 파일 존재·크기도 함께 확인합니다. 원본 내용 전체를 해시 비교하는 방식은 아니므로 같은 식별 정보로 파일 내용만 바뀐 경우에는 수동 강제 실행이 필요합니다.

예약은 서버 내부 APScheduler에서 실행됩니다. 서버 중지 중 실행이나 실패 직후 자동 재시도는 보장하지 않으며, 원인 해결 후 수동 실행하거나 다음 예약 시점에 다시 확인합니다.

**정제·발행·적재 원칙**

- 실행 잠금으로 배치 중복 실행을 제한합니다.
- 지역 코드가 잘못된 행은 제외하고 사유를 기록하며, 대상 행이 0건이면 발행하지 않습니다.
- 모든 임시 파일을 검증한 뒤 서비스 파일을 개별 교체하고 manifest를 마지막에 발행합니다.
- 워커 초기화 이후 사전 적재하며, 재적재 전후 세대·파일 서명을 확인한 뒤 메모리 캐시를 교체합니다.

원본 누락·검증 실패·교체 및 적재 오류의 대응과 한계는 [7번 예외처리 구조](#exception-handling)에 정리했습니다.

### 6-3. CSV 파일 구성과 연결 기준

| 자료 | 원본 파일 (`data/`) | 서울 서비스 파일 (`data/Batch/`) | 활용 |
|---|---|---|---|
| 공공체육시설 프로그램 | `public_sports_program.csv` | `public_sports_program_seoul.csv` | 강좌 검색·비교 |
| 스포츠강좌이용권 이용현황 | `sports_voucher_usage.csv` | `sports_voucher_usage_seoul.csv` | 지역·종목 집계 및 AI 분석 근거 |
| 체육시설 현황 | `sports_facility_status.csv` | `sports_facility_status_seoul.csv` | 시설 조회·후보 선정 |
| 시설 인접 교통 | `facility_transit.csv` | `facility_transit_seoul.csv` | 시설별 대중교통 조회 |

`_seoul`은 서울 범위로 정제한 파일을 뜻합니다. 서로 다른 출처의 CSV에 공통 PK·FK가 있다고 가정하지 않고 다음 업무 기준으로 연결합니다.

| 연결 대상 | 기준 |
|---|---|
| 이용현황 내부 시설·강좌 | 지역 코드·시설명·주소·상세주소·강좌번호 등 집계 식별 기준 |
| 시설 ↔ 교통 | 정규화된 시설명 + 위도·경도 소수점 6자리 |
| 종목 ↔ 시설 후보 | 종목·시설유형/업종 대응표 + 지역 + 운영상태 |
| 서비스 CSV ↔ manifest | 세대·파일 크기·수정시각·SHA-256 등 파일 검증 정보 |

### 7-1. 프로그램 설계 흐름

[이미지 크게 보기](docs/readme-assets/program-design-flow.png) · [SVG 원본](docs/readme-assets/program-design-flow.svg)


1. **지역 선택:** 지도·행정구역에서 지역을 조회하고 이용 시설·강좌·신청 실적·종목 분포를 확인합니다.

2. **종목·시설 선택:** 정상운영 후보의 상세·교통 정보를 확인하고 최대 20곳을 선택합니다. 실제 후보가 없을 때만 동의 후 시설 미정으로 진행합니다.

3. **정보 입력:** 프로그램명·모집인원·수강료·대상·기간·내용을 입력합니다. 수강료는 천 단위 쉼표로 표시하고 서버에는 정수로 전달합니다.

4. **AI 검토 또는 생략:** 현재 입력의 유효한 AI 결과가 있거나 AI 없이 생성하기를 선택해야 계획서를 완성할 수 있습니다.

5. **완성과 복원:** 생성 이후에도 STEP 03을 유지합니다. 최근 5건 복원·인쇄 시 AI를 재호출하지 않습니다.

6. **처음으로:** 입력·시설·화면의 AI 상태를 초기화하고 STEP 01 상단으로 이동합니다. 최근 5건과 서버 지역 AI 캐시는 삭제하지 않습니다.

| 구분 | 지역 현황 분석 | 프로그램 AI 검토 |

| 분석 근거 | 지역·종목별 집계와 자료 기간 | 집계 자료 + 선택 시설 + 프로그램 입력 |

| 결과 활용 | 지역 프로그램 기획 참고 | 사용자가 선택한 유효 결과를 계획서에 포함 |

**공통 처리**

1. **요청 구성:** 필요한 집계·시설·입력 정보와 분석 지침·응답 JSON 스키마를 구성합니다. 원본 CSV 전체 업로드나 모델 사전 학습은 수행하지 않습니다.
2. **AI 호출:** 서버의 `google-genai` SDK로 Gemini를 호출하며 API 키는 서버에서 관리합니다. 유효한 지역 캐시가 있으면 외부 호출 없이 재사용합니다.
3. **검증·제공:** JSON 구조·근거 키·점수를 검증합니다. 프로그램 종합 점수와 등급은 서버에서 계산하며, 평가 가능한 점수가 모두 없으면 **판단 자료 부족**으로 표시합니다. 통신·응답 오류는 아래 예외처리 항목을 따릅니다.

**입력 변경과 결과 유지**

- 지역 조회만으로 AI를 호출하지 않습니다. 다른 지역을 조회하면 이전 결과를 참고용으로 유지하고 재분석이 필요한 상태를 알립니다.
- 프로그램의 동일 입력에 대한 유효한 결과가 있으면 재분석을 제한합니다. 입력이 바뀌면 이전 결과는 유지하되 계획서 포함 선택을 해제합니다.
- 계획서에는 생성 당시 선택한 결과를 고정하며, 생성·인쇄·최근 목록 복원에서는 AI를 다시 호출하지 않습니다.

**기동 대기 문제 개선:** Gunicorn master에서 CSV 갱신 스레드를 시작하면 fork 후 잠금·스레드 상태가 불일치할 수 있어, 워커 초기화 이후 적재와 스케줄러를 시작하도록 분리했습니다. 준비 상태와 PID별 `CSV_DIAG` 로그로 추적합니다.


**AI 진단:** 요청 ID로 처리 단계·SDK 설정·응답 상태·오류 분류를 기록합니다. API 키·사용자 작성 내용·AI 응답 본문은 로그에 남기지 않습니다. 프로세스당 AI 분석은 1건으로 제한합니다.

### 7-4. 주요 정책 크롤링 흐름

문화체육관광부의 체육정책 목록에서 **제목과 원문 링크를 최대 10건 추출**하여 제공합니다. 정책 본문과 첨부파일은 수집하지 않으며, 사용자가 원문을 새 창으로 열어 확인합니다.

![주요 정책 크롤링 아키텍처](docs/readme-assets/policy-crawling-architecture.png)

[이미지 크게 보기](docs/readme-assets/policy-crawling-architecture.png) · [SVG 원본](docs/readme-assets/policy-crawling-architecture.svg)

1. **조회 요청:** 주요 정책 보기 클릭 즉시 로딩 다이얼로그를 표시하고, HTMX로 Django 서버에 목록을 요청합니다.
2. **캐시 확인:** 프로세스 메모리에 유효한 결과가 있으면 재사용합니다. 성공 결과는 15분, 실패 결과는 60초 동안 보관합니다.
3. **수집·파싱:** 캐시가 없거나 만료되면 `urllib.request`로 목록 HTML을 조회하고, BeautifulSoup으로 제목·링크를 추출합니다. 요청 타임아웃은 6초, 읽기 크기는 최대 2,000,000바이트이며 동일 호스트의 HTTP(S) 링크만 허용합니다.
4. **화면 반영:** 결과를 캐시에 저장하고 HTML 조각을 반환하여 로딩 화면을 목록으로 교체합니다. 통신·목록 추출 실패 또는 브라우저 요청 실패 시 다이얼로그 안에 오류를 안내합니다.

**CSV 월간 배치와 독립된 요청 기반 기능입니다.** 서버 크롤링은 동기 처리이며, 실패 캐시의 60초가 지나도 자동 재시도하지 않습니다. 캐시 만료 후 다음 조회 요청에서 다시 수집합니다.

## 9. 한 줄 회고

#### 홍석환
좋은 팀원들과 함께 아이디어를 구체화하고 하나의 서비스로 만들어가는 과정을 경험할 수 있어 뜻깊었습니다. 기획부터 UI 구성과 수정, 다양한 프레임워크와 라이브러리를 활용한 구현까지 참여하며, 개별 코드가 서로 연결되어 서비스로 작동하는 흐름을 이해할 수 있었습니다. 특히 AI를 활용한 바이브 코딩은 구현의 진입 장벽을 낮추고 여러 아이디어를 빠르게 시도하는 데 도움이 되었습니다. 동시에 원하는 결과를 얻으려면 요구사항을 구체적으로 정의하고, 생성된 코드의 동작과 결과를 직접 검토하는 과정이 중요하다는 점도 배웠습니다. 이번 프로젝트는 코드를 작성하는 것을 넘어, 사용자의 관점에서 기능과 화면을 다듬고 서비스 전체의 연결을 고민해 본 경험이었습니다.

#### 서정길
프로젝트 수행 과정 전반에 AI를 활용했다는 점이 새롭게 다가왔습니다. 기존이었다면 처음 접해보는 파이썬 Django 프레임워크와 Render 서비스 구축 과정에서 많은 시간을 허비했겠지만, AI를 활용하면서 발생하는 오류를 직접 확인하고 해결해 나갈 수 있었습니다. 다만 현재 제공되는 데이터셋이 CSV 형태로만 구성되어 있어 엔터프라이즈급 기능으로 확장하는 데 한계가 있었던 점은 아쉬움으로 남았습니다. 추후 신규 프로젝트를 구축할 때에는 초기 단계부터 데이터 구조와 저장 방식에 대한 설계를 좀 더 상세하게 진행해야겠다고 생각했습니다.

#### 설호현
담당 기능을 구현하는 것만큼 예외 상황을 어떻게 처리할지 고민하는 일도 중요하다는 것을 다시 배웠습니다. 처음으로 전국 단위 CSV를 서울 데이터로 정제하면서 ‘서울’과 ‘서울특별시’처럼 다른 표기를 통일하고, 구 이름만 남은 행은 지역 코드와 주소를 확인해도 서울로 특정할 수 없으면 제외했습니다. 이 과정을 통해 데이터를 쓰기 전에 그 의미와 품질을 확인하는 일이 얼마나 중요한지 느꼈고, 이번에는 데이터 정제 과정을 익히기 위해 CSV를 사용했지만 앞으로는 정제한 데이터를 DB에 적재하고 갱신하는 방식도 구현해 보고 싶습니다.

## 10. 현재 제약사항 및 향후 개선사항

### 10-1. 현재 제약사항


- 대시보드는 서울 중심이며 시설 후보가 공공시설로만 제한되지는 않습니다.

- 대관·강사·접수·결제·개설 확정과 실제 문자·카카오톡 발송은 구현 범위 밖입니다.

- 최근 계획서는 해당 브라우저 5건이며 계정·기기 간 동기화가 없습니다.

- AI 재시도는 수 분 걸릴 수 있으며 프록시 제한으로 먼저 연결이 종료될 수 있습니다.

- 프로세스 간 전역 AI 호출 제한, 사용자별 할당량, 일일 비용 제한은 미구현입니다.

- 파일 캐시는 배포 환경에 따라 초기화될 수 있습니다. 실제 기관 도입·정량적 효과는 별도 검증이 필요합니다.

### 10-2. 향후 데이터 구조 확장

![현재 서울 CSV 구조와 향후 전국 DB 구조 비교](docs/readme-assets/data-expansion-flow.png)

[이미지 크게 보기](docs/readme-assets/data-expansion-flow.png) · [SVG 원본](docs/readme-assets/data-expansion-flow.svg)

| 방향 | 개선 계획 |
|---|---|
| 원본 수집 자동화 | 데이터별 실제 갱신일·주기를 확인하고, 원본 제공 API가 마련되면 수집·검증 단계를 기존 정제 작업 앞에 연결합니다. 현재 자동 수집기는 미구현이며 정제·반영 단계가 분리되어 있습니다. |
| 전국 데이터·DB 전환 | 전국 조회에 맞는 DB 스키마·지역/종목 색인·조회 계층을 구현합니다. 현재 `data_refresh.py`에 CSV/DB 저장기 선택 지점은 있으나 DB 저장기와 조회 전환은 추가 개발이 필요합니다. |
| 배치 신뢰성 | 서버와 독립된 예약 실행, 실패 알림·제한된 재시도, 원본 체크섬 비교와 여러 파일의 일괄 발행을 보완합니다. |
| 최신성 표시 | 기관 원본의 기준일·갱신일과 서비스 반영일을 구분하여 사용자가 자료의 최신성을 확인하도록 개선합니다. |

## 부록 · 실행 및 참고 자료

### 실행 및 환경 설정


<details>

<summary><strong>로컬 실행 명령과 AI 환경변수</strong></summary>


Python 가상환경에서 `main/requirements.txt`를 설치하고 원본 데이터를 준비합니다. 데이터 압축 해제·배치·운영 배포의 세부 절차는 [Render 배포 안내](docs/RENDER-DEPLOYMENT.md)를 참고합니다.


```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r main/requirements.txt
.\.venv\Scripts\python.exe main/manage.py migrate
.\.venv\Scripts\python.exe main/manage.py runserver 127.0.0.1:8000
```


루트 `.env` 예시:


```dotenv
AI_MODE=live
AI_PROVIDER=gemini
AI_MODEL=gemini-3.1-flash-lite
AI_TIMEOUT_SECONDS=25
AI_MAX_RETRIES=10
GEMINI_API_KEY=발급받은_API_키
AI_REVIEW_INCLUDE_TRANSIT=false
```


외부 호출 없는 동작 확인에는 `AI_MODE=dummy`를 사용합니다. 더미 결과는 실제 AI 검토 성과와 구분합니다. Render에서는 같은 변수를 Environment에 등록하며 기존 OS·Render 환경변수가 `.env`보다 우선합니다. 실제 `.env`와 API 키는 Git에 포함하지 않습니다.
