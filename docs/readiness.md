# 목록 준비 상태와 초기화 안내

CSV 목록이 아직 메모리에 없을 때 화면이 이유를 말하게 한다. 예전에는 같은 상황에서
접속이 응답 없이 대기하거나, 원본이 없으면 모든 요청이 500으로 끊겼다.

## 무엇이 바뀌었나

```text
app/runtime/readiness.py    준비 상태 판정. 화면·상태 점검·게이트가 같은 답을 쓴다.
app/runtime/middleware.py   미준비 요청을 요청 형식에 맞는 503으로 돌려보낸다.
app/runtime/csv_warmup.py   첫 적재도 감시 스레드가 맡는다.
templates/runtime/not_ready.html  외부 자산에 기대지 않는 안내 화면.
main/urls.py                /healthz/ 를 준비 상태에 연동하고 /readyz/ 를 추가.
```

## 첫 적재를 스레드로 옮긴 이유

`start_csv_warmup()`은 `main.wsgi` 임포트 시점에 불린다. gunicorn은 WSGI 모듈을 다
읽은 뒤에야 요청 처리를 시작하므로(`preload_app = False`), 예전처럼 여기서 동기로
적재하면 그동안 들어온 접속이 응답도 안내도 없이 대기했다. 서울 자료 기준 약 4.4초다.

적재를 스레드로 옮기면 워커가 곧바로 요청을 받는다. 자료가 필요 없는 화면(정책,
배치 관리, 상태 점검)은 즉시 열리고, 목록 화면은 안내를 받는다. 적재가 끝나기 전에
목록이 요청되면 `VersionedCsvCache.get()`이 기존처럼 그 요청 안에서 읽는다. 감시
스레드가 이미 읽고 있으면 같은 잠금에서 기다렸다가 완료 즉시 응답하므로, 중복
적재도 무응답도 생기지 않는다.

## 상태 다섯 가지

| 상태 | 뜻 | 화면 |
|---|---|---|
| `ready` | 필요한 목록이 모두 메모리에 있다 | 정상 |
| `loading` | 적재 진행 중 | **막는다** — 안내 + 자동 재시도 |
| `missing` | 원본 CSV가 없다 | **막는다** — 배치 실행 안내, 재시도 없음 |
| `stalled` | 감시 스레드가 없거나 시한 초과 | 통과 |
| `disabled` | `CSV_WARMUP_ENABLED=false` | 통과 |

`stalled`를 막지 않는 것이 중요하다. 그 경로에서는 요청이 직접 읽으므로, 막으면
아무도 적재하지 않아 화면이 영원히 안내문에 머문다. 사전 적재를 시작한 적이 없는
프로세스(관리 명령, 테스트)도 같은 이유로 `stalled`다.

## 판정은 최초 적재만 본다

배치가 새 세대를 발행해 다시 읽는 동안에도 캐시는 옛 목록을 그대로 서비스한다
(`get()`의 `background_refresh` 경로). 갱신 중을 미준비로 보면 **매주 일요일 00시에
멀쩡한 자료를 두고 사이트 전체가 안내 화면이 된다.** 그래서 게이트는
`VersionedCsvCache.is_loaded`, 즉 최초 적재 여부만 본다.

## 화면마다 기다리는 목록이 다르다

`middleware.ROUTE_REQUIREMENTS`가 경로와 필요한 목록을 잇는다. 시설 목록은 약
0.4초, 이용현황은 0.6초, 프로그램은 3.4초가 걸리므로, 전체를 한 덩어리로 묶으면
시설 화면이 프로그램 적재를 기다린다. `targets.py`도 가벼운 자료부터 적재한다.

교통 상세 색인은 사전 적재 대상이 아니고 게이트 조건에도 넣지 않는다. 넣으면 시설
상세를 누를 때마다 화면이 미준비로 보인다.

## 응답 형식을 요청에 맞춘다

| 요청 | 응답 |
|---|---|
| htmx 조각 | `503` + `HX-Refresh: true` — 조각 자리에 문서를 넣지 않는다 |
| 설계 마법사 `fetch` | `503` JSON — `program-planner.js`의 `response()`가 `error`를 읽는다 |
| `*.xlsx` | `503` `text/plain` — 깨진 파일을 내려받지 않게 한다 |
| 일반 페이지 | `503` 안내 화면 |

모든 거절에 `Cache-Control: no-store`와 `Retry-After`를 붙인다. 준비된 뒤에도 안내가
어딘가에 남아 보이면 안 된다.

## /healthz/ 를 준비 상태에 묶은 이유

Render는 이 경로로 새 인스턴스의 투입 시점을 정한다. 예전에는 적재가 끝나야 워커가
응답을 시작해 이 보호가 자연히 걸렸다. 적재를 스레드로 옮기면 그 보호가 사라지므로,
준비 전에는 `503`을 명시한다. 이렇게 하지 않으면 **배포할 때마다 모든 사용자가 초기화
화면을 본다.** 안내 화면이 실제로 보이는 경우는 워커 재시작과 원본 누락뿐이다.

`/readyz/`는 목록별 적재 여부와 원본 존재 여부를 함께 준다. 배치 관리 화면의
`서비스 목록 적재 상태` 표가 같은 값을 쓴다.

## 설정

| 이름 | 기본값 | 뜻 |
|---|---|---|
| `CSV_WARMUP_ENABLED` | `true` | 이 프로세스가 사전 적재를 맡는가 |
| `CSV_REFRESH_INTERVAL_SECONDS` | `5` | 세대 변경 확인 주기 |
| `CSV_READY_TIMEOUT_SECONDS` | `120` | 이 시간을 넘기면 안내를 걷고 통과시킨다 |

## 검증

`app/runtime/test_readiness.py` 22개. 판정 우선순위, 화면별 대기 목록, 응답 형식
분기, `/healthz/`·`/readyz/` 응답을 확인한다. 실제 서버로도 적재 중 `loading`,
원본 삭제 시 `missing`, 준비 후 정상 응답을 확인했다.
