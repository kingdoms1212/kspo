# 프로그램 설계 전환 검토안

## 시안 개정: 시설 상세 선택 + 키오스크 스타일

- 2026-09-15 추가 요청 반영. 이 개정 내용은 아래 초기 시안의 화면 배치 설명보다 우선한다.
- 상단 3개 메뉴, 큰 터치 버튼(주요 버튼 54px 이상), 단계 카드, 넓은 입력 영역으로 키오스크 스타일 적용. 실제 전용 키오스크 모드·장치 제어는 구현하지 않는다.
- 지역 현황 → 종목·시설 → 입력을 단계별로 표시한다. 기존 현황 데이터 영역은 첫 단계에 유지하며 ‘지역 현황으로’로 돌아갈 수 있다.
- 시설 선택은 좌측 후보 목록 + 우측 상세정보. 사진·소재지·유형·종목·운영상태·연결 근거·운영기관/연락처·면적/수용인원·인접 교통 영역을 표시한다. 작은 화면은 목록 아래 상세정보를 배치한다.
- 시설 상세 열기는 체크 선택을 바꾸지 않는다. 목록의 체크박스와 상세의 ‘계획서에 포함하기’는 동일한 선택 상태를 공유한다. 확정·재선택 시 선택값과 프로그램 입력을 보존한다.
- 연락처·면적·정류장 등 없는 값은 미제공으로 표시한다. 시설과 연결 근거는 여전히 예시이며 실제 데이터를 연결하지 않았다.
- 브라우저 검증: 상세 대상 변경, 상세에서 선택 후 확정, 재선택 시 체크와 입력값 보존. JavaScript 구문 검사 통과.

검토일: 2026-09-15. 사용자 제공 3개 화면과 현재 소스 기준. 이 폴더는 검토 문서와 독립 시안이며 운영 앱·원본 CSV는 변경하지 않았다. 시안의 시설명·지역별 수치·연결 근거는 동작 설명용 예시다. 기존 사진은 대표 이미지로만 사용한다.

## 1. 메뉴와 범위

| 메뉴 | 역할 | 기존 코드 재사용 |
|---|---|---|
| 프로그램 설계 | 지역 현황을 근거로 시설과 운영 조건을 정해 설계안 생성 | dashboard 집계·지도 + 신규 설계 서비스 |
| 프로그램 현황 | 원자료 등록 프로그램 조회, 별도 탭으로 내 설계안 재조회 | programs 검색·표·엑셀 |
| 시설 현황 | 시설 조회·상세·인접 대중교통 | facilities 및 transit |

‘프로그램 선택’보다 ‘프로그램 설계’를 권장한다. 기존 프로그램 선택이 아니라 사용자가 이름·모집인원·수강료를 새로 정의하기 때문이다. 생성 결과는 설계안이며 시설 대관·강좌 개설·모집 게시가 자동 확정되는 것은 아니다. ‘내 설계안’ 탭은 초기화 후 결과를 다시 찾기 위한 제안이다. 기존 프로그램 집계와 생성안을 합산하지 않는다.

## 2. 현재 코드에서 확인한 사항

- 현재 실행 구조는 React가 아닌 Django 템플릿 + HTMX + JavaScript다. 이 기능 때문에 프레임워크를 교체할 필요는 없다.
- `main/app/dashboard/services.py::dashboard_data(region)`는 지역별 KPI·종목 상위 5개를 집계한다. 시군구 선택까지 원하면 district 인수와 동일 범위의 집계가 추가로 필요하다.
- 공통 `main/static/region-map.js`는 시도/시군구 GeoJSON과 `regionmap:select` 이벤트를 담당하며 화면별 지도 동작 스크립트로 연결된다. 지도 확대와 데이터 필터 변경을 한 상태로 동기화해야 한다.
- 대시보드는 `스포츠강좌이용권 이용현황 정보.csv`, 프로그램은 `공공체육시설 프로그램 정보.csv`, 시설은 `전국체육시설현황 데이터.csv`를 읽는다. 모집 대상·모수·관측시점이 같지 않다.
- facilities 검색은 region/industry/flag/state/owner/query를 제공한다. 종목 일치·시군구 필터·프로그램 연결 근거를 반환하는 후보 조회 서비스는 별도로 필요하다.
- `Facility`와 `Program`은 CSV namedtuple이다. 현재 `facility-행번호`, `program-행번호`는 CSV 재정렬 시 바뀔 수 있어 생성안을 저장할 외래키로 사용할 수 없다.
- `Facility`에는 종목 다대다 목록이 없고 `industry`, `facility_type`이 있다. `Program.sport`는 자유입력 유형, 없으면 시설 업종을 대입한다. 이 값을 그대로 종목 select에 노출하면 일관성이 없다.
- `common.data.facility_key`는 행정코드+시설명+도로명주소의 완전한 키만 허용한다. 그러나 이것만으로 현재 전국 시설 자료와 프로그램 전체가 연결된다고 보장하지 않는다. 과거 문서의 연결률은 원천이 달라졌으므로 이번 구현의 수치로 재사용하지 않는다.
- DB 설정은 SQLite이지만 설계안·선택시설·발송 이력 모델은 현재 기능에 없다. 신규 영속 저장과 권한 처리가 필요하다.

## 3. 화면별 명세

### A. 프로그램 설계: 지역 현황

기존 4개 KPI, 지도, 시군구별 신청인원, 종목별 신청인원을 유지한다. 정책 참고 지표는 기존 데이터 범위에서 보조 영역으로 유지할 수 있다. 시안은 핵심 흐름 검토를 위해 보조 지표를 축약했다.

- 전국은 탐색 상태. 시도 또는 시군구를 선택한 뒤 ‘프로그램 생성하기’를 활성화한다.
- 지도 클릭과 지역 select는 같은 필터 상태를 변경한다. KPI·차트·제목·후보시설 조건이 같은 지역을 가리켜야 한다.
- 선택 지역, 행정구역 코드, 출처, 관측기간을 상태에 저장한다. 종목 상위 5개 차트는 참고자료이며 종목 선택지는 검증된 전체 종목 사전으로 구성한다. 상위 5개에 없는 농구도 선택할 수 있어야 한다.
- 동시 요청에서는 최신 지역의 응답만 적용한다. 로딩 중 이전 지역 값을 새 제목 아래 표시하지 않는다.

### B. 종목과 시설 선택

‘프로그램 생성하기’ 클릭 후 하단 선택 영역을 펼치고 종목 select로 포커스를 이동한다. 농구 선택 시 해당 지역·종목의 후보를 조회한다.

**가로 캐러셀보다 세로 목록을 권장한다.** 사진·시설명·주소·운영상태·연결 근거를 같은 열에서 비교하고 체크하기 쉽다. 데스크톱은 높이 제한 목록 + 하단 선택 개수/확정 버튼, 모바일은 한 열 목록이다. 실제 대량 결과는 서버 페이지네이션(예: 20건) 또는 더 보기로 처리하며 페이지를 바꿔도 선택 ID를 유지한다.

- 직접적인 농구 시설 유형 또는 검증된 농구 강좌 이력이 있는 시설만 근거와 함께 표시한다.
- ‘다목적체육관’이라는 이름만으로 농구 가능 시설로 자동 확정하지 않는다. 이력 존재도 현재 대관 가능을 뜻하지 않는다.
- 운영상태는 정상운영을 기본으로 한다. 삭제·폐업 제외, 상태 미확인/종목 근거 미확인은 별도로 안내하고 기본 후보에서 제외한다.
- 목록 0건, 매핑 미확인, 조회 오류를 구분한다. ‘후보 없음’을 ‘농구 시설이 실제로 없음’으로 표현하지 않는다.
- 1개 이상 선택 시 확정 활성화. 선택 단계는 아직 확정이 아니다.

### C. 시설 확정·재선택과 입력

확정한 시설은 하단 요약 목록으로 남기고 입력 폼을 펼친다. ‘시설 재선택’으로 기존 체크 상태를 복원한다. 재확정까지 생성 버튼을 비활성화하며 프로그램명·설명 등 입력은 유지한다.

| 필드 | 제안 검증 |
|---|---|
| 프로그램명 | 필수, 공백만 불가, 최대 100자 |
| 모집인원 | 필수 양의 정수. 기본안은 시설당 동일 인원. 전체 인원=시설당 인원×시설 수 |
| 프로그램 설명 | 필수, 최대 2,000자, HTML은 실행하지 않음 |
| 수강료 | 필수 0 이상의 정수 원, 0은 무료. 1인 기준임을 명시 |
| 수강료 기준 | 월/회/전체 과정 중 필수 선택 |
| 대상 | 선택 입력. 실제 모집 게시로 확장할 때 필수화 검토 |
| 시작·종료일 | 선택 입력. 입력했다면 시작일≤종료일 |

상한은 서비스 운영 정책으로 확정해야 한다. 시안의 인원/금액 상한은 예시다. 시설 수용인원은 전체 건물 기준일 수 있으므로 강좌 모집인원의 검증값으로 바로 사용하지 않는다. 시설별 다른 인원·금액이 필요하면 연결 테이블에 개별 값을 저장하는 2차 기능으로 확장한다.

지역·종목 변경은 선택·확정시설을 무효화한다. 입력 글은 보존하되 변경 안내를 제공한다. 처음 시작하는 전국 상태와 재선택 상태를 혼동하지 않도록 단계 표시를 둔다.

### D. 생성 결과 팝업

안전한 처리 순서: 서버 검증 → 트랜잭션으로 설계안과 근거 스냅샷 저장 → 성공 결과 확보 → 작성 화면 초기화 → 저장된 결과 팝업 표시. 저장 실패 시 초기화하지 않는다. 중복 클릭에는 멱등키를 사용한다.

팝업은 생성 전 지역·기간·KPI·종목별 현황, 선택시설 기본정보와 연결 근거, 프로그램 입력값, 생성일·설계안 ID를 표시한다. 현재 화면을 다시 읽어 결과를 구성하면 초기화로 값이 사라지므로 저장된 스냅샷을 사용한다. 지도까지 인쇄할 경우 지도 SVG/이미지도 별도 스냅샷으로 확보한다. 시안 팝업은 지도 대신 동일 지역·지표·종목 수치로 근거를 보여준다.

닫기/Escape 후에도 ‘최근 생성안 보기’ 또는 프로그램 현황의 ‘내 설계안’에서 재조회할 수 있어야 한다. 인쇄 시 배경 화면·메뉴·버튼은 제외하고 A4 페이지 넘김을 처리한다.

### E. 프로그램 현황 / 시설 현황

- 프로그램 현황: 기존 필터·요약·대표 카드·비교표·엑셀을 유지. ‘추천’ 문구는 실제 추천 알고리즘이 없다면 ‘조회 결과’로 정리. 내 설계안은 별도 탭과 상태로 구분한다.
- 시설 현황: 기존 검색·목록·상세·교통 UI 유지. 종목 연결 근거와 기준시점 표시를 추가한다. 대표사진은 실제 시설사진처럼 표현하지 않는다.
- 시안의 두 메뉴는 배치 검토용이며 검색·내보내기·실제 교통 조회를 연결하지 않았다.

## 4. 데이터와 구현 제약

1. **지역 정규화**: ‘서울’/‘서울특별시’, 코드 길이 차이, 관리 시군구와 소재지 시군구, 행정구역 개편을 검토한다. 코드·원문·유효기간을 가진 명시적 대응표를 두며 ‘전남광주’ 같은 통합 이름을 임의 분배하지 않는다. 미대응 지역은 분석은 가능해도 자동 후보 연결은 제한한다.
2. **종목 사전**: Sport의 표준코드/명칭과 SportAlias 원문을 분리한다. 업종·시설유형·프로그램명에서 추정된 종목과 직접 확인된 종목을 구분하고 근거·검수상태를 기록한다. 첫 단계는 농구 등 검증 가능한 종목부터 개방한다.
3. **시설 식별**: 안정 UUID와 원천 레코드 연결 테이블을 도입한다. 원천키가 없으면 정규화 복합키+충돌 검수로 연결한다. 같은 이름만으로 다른 지점을 합치지 않는다.
4. **과거 이용≠현재 수요**: 신청인원은 2020~2026 개설월 합계가 섞인다. 지역별 모수와 최신성도 다르다. 순위는 설계 참고이며 수요예측·대관 가능·강좌 모집 가능을 보장하지 않는다.
5. **성능**: 원본 CSV를 클릭할 때마다 조인하지 않는다. 원천 버전별 정규화/인덱스를 사전 생성하고 지역·종목·정상운영 인덱스로 조회한다. 응답에 원천 버전과 매핑 상태를 포함한다.
6. **지도**: 현재 2013년 GeoJSON은 최신 행정경계와 차이가 있을 수 있다. 공통 지도 오류 시 지역 select를 대체 수단으로 유지한다. 시군구 선택과 집계 코드가 같은 경계 버전을 사용하도록 정비한다.
7. **저장·권한**: 담당자 로그인, 생성안 소유권/열람권한, CSRF, 서버 검증, 중복 생성 방지가 필요하다. 내부 데이터에 접근하는 공유 링크는 만료·취소 가능한 임의 토큰과 공개 필드 제한을 권장한다.

## 5. 프린트·문자·카카오톡

- 프린트: 브라우저 인쇄와 인쇄 전용 CSS로 1차 구현 가능. PDF가 필요하면 브라우저의 PDF 저장을 사용할 수 있다. 서버 PDF 파일 생성은 별도 기능이다.
- 문자: 외부 SMS/LMS 사업자 계정, API 인증, 인증된 발신번호, 과금, 수신번호 입력, 발송결과 확인이 필요하다. 공공시설 전화번호를 수신자로 자동 사용하지 않는다. 내용 미리보기→명시적 발송으로 처리한다. 긴 문서는 본문 전체 대신 요약과 접근 가능한 결과 링크를 권장한다. 요청 접수와 실제 전달 완료를 구분하고 재시도 중복발송을 막는다.
- 카카오톡: 1차는 **카카오톡 공유**를 권장한다. 사용자가 직접 친구/대화방을 선택하며 Kakao JavaScript SDK와 앱/도메인 설정이 필요하다. 임의 전화번호로 자동 전송하는 기능이 아니다. 발송 완료를 단순 클릭만으로 표시하지 않는다. 공유 결과 링크는 수신자가 접근할 수 있어야 한다.
- 전화번호 기반 알림톡이 필요하면 카카오톡 공유와 별도 범위로 채널·발송 사업자·템플릿 등 요건을 검토해야 한다. 이번 시안에는 실제 통신을 연결하지 않았다.

## 6. 제안 코드 구조와 저장 모델

기존 모듈명을 즉시 바꿀 필요는 없다. 표시 메뉴를 먼저 변경하고 신규 쓰기 기능을 `app/planning`으로 분리한다.

```text
app/dashboard/      기존 읽기 집계, 지역·시군구 필터 확장
app/programs/       원본 등록 프로그램 조회
app/facilities/     시설 조회, 종목 근거 기반 후보 조회
app/planning/       forms/models/services/views/urls/tests, 설계안 저장·재조회·인쇄
app/common/         지역·종목 표준화, 원천 버전, 시설 식별
app/notifications/  후속 문자 발송 어댑터·결과·재시도 처리
```

| 모델 | 주요 필드 |
|---|---|
| ProgramPlan | UUID, 작성자, 제목, 지역코드, 종목코드, 설명, 모집인원 기준, 1인 수강료/단위, 운영기간, 상태, 생성일, 멱등키 |
| PlanFacility | plan FK, 안정 facility UUID, 시설 기본정보 스냅샷, 매핑 근거/원천 버전, 시설별 모집인원 |
| PlanSnapshot | plan FK, 필터, 원천 파일/버전/기간, KPI, 시군구 집계, 종목 집계, 지도 경계 버전 |
| Sport / FacilitySport | 표준 종목, 시설별 종목, 연결 근거, 관측기간, 검수상태 |
| ShareLink / DeliveryAttempt | 만료·취소 토큰, 공개범위 / 채널, 결과 상태, 사업자 메시지 ID, 중복방지키 |

제안 엔드포인트: GET `/planning/summary`, GET `/planning/facilities`, POST `/planning/plans`, GET `/planning/plans/<uuid>`, GET `/planning/plans/<uuid>/print`, POST `/planning/plans/<uuid>/sms`. 구체적인 경로는 기존 URL 체계에 맞춰 확정한다. 시설과 지역 조건은 POST에서 다시 검증한다.

## 7. 구현 순서·수용 조건

1. 지역/종목/시설 연결 품질 점검과 매핑 사전 작성. 운영 대상 지역·종목 확정.

3. DB 저장·권한·스냅샷·실패 시 보존·중복 방지·재조회·인쇄.

## 8. 이번 시안 사용법과 경계

`index.html`을 프로젝트 루트에서 정적 서버로 열어 확인한다. 예: `python -m http.server 8010 --bind 127.0.0.1` 실행 후 `/docs/program-design-review/` 접속.

서울·경기·부산 중 지역 선택 → 프로그램 생성하기 → 농구 → 시설 체크 → 확정 → 프로그램 정보 입력 → 설계안 생성하기. 시설 재선택, 생성 후 초기화, 결과 다시 열기, 인쇄, 문자/카카오 전달 내용 미리보기를 제공한다. 결과는 메모리에만 있으며 새로고침하면 사라진다. 실제 저장 성공·실제 전송 성공을 시뮬레이션하지 않는다.

포함 리소스: ECharts 5.6.0(원본 Apache 라이선스 헤더 유지), 현재 앱에서 사용하는 southkorea/southkorea-maps kostat/2013 시도 GeoJSON. 시안 한정 경계 데이터이며 최신 행정구역 검증 자료가 아니다. 원본: https://github.com/southkorea/southkorea-maps/tree/master/kostat/2013/json

확정이 필요한 운영 정책: 복수 시설의 인원·수강료를 동일하게 적용할지, 설계안 소유·공유 대상, 실제 개설을 포함할지, 문자 사업자, 카카오 공유 vs 알림톡. 본 검토안은 ‘시설별 동일 조건, 내부 담당자의 설계안, 카카오 공유’를 기본으로 작성했다.
