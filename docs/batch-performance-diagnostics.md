# CSV 배치 속도 차이 진단

## 코드 검토 결과

- `scripts/build_render.py`는 웹 서버 기동 전에 `prepare_render_data`를 실행합니다.
- 화면 강제 실행은 `manual_runner.py`에서 별도 관리 명령 프로세스를 생성합니다.
- 두 경로는 `refresh_region_data`를 거쳐 같은 `refresh_region_csvs`와 `_extract_to_part`를 실행합니다.
- `force_refresh=True`는 원본 변경이 없을 때 생략하는 조건만 건너뜁니다. 행 단위 처리에는 차이가 없습니다.
- 화면 진행률 저장 콜백은 파일 추출 후 호출됩니다. 제공된 파일별 추출 시간 자체가 약 9~10배 늘어난 원인으로 설명하기 어렵습니다.
- 운영 파일 교체와 manifest 발행은 전체 추출 후 이루어집니다. 새 세대로 인한 메모리 캐시 재적재가 이번 배치의 모든 파일 추출을 느리게 했다고 볼 근거는 없습니다. 다른 기존 작업과의 자원 경쟁 가능성은 남아 있습니다.

## 추가된 화면 로그

`BATCH_DIAG` 접두어로 기존 배치 로그에 기록하며 별도 설정은 필요 없습니다.

- 실행 환경: PID, 부모 PID, 강제 실행 여부, 진행률 콜백 여부, Python 버전, 논리 CPU 수, 입출력 경로
- 파일별 추출: 실제 경과 시간(`wall`), 현재 배치 스레드의 CPU 시간(`thread_cpu`), 두 시간의 비율, 초당 처리 행 수, 원본 바이트 수
- 파일별 디스크 동기화: `fsync` 소요 시간

`cpu_count`는 컨테이너의 실제 CPU 할당량이 아닙니다. `thread_cpu / wall`도 서버 전체 CPU 사용률이 아니라 해당 스레드가 측정 구간에서 CPU를 사용한 비율입니다.

## 비교 방법

재배포 시 최초 실제 추출 로그와, 이후 강제 최신화 1회의 로그를 비교합니다. 최초 실행이 원본 변경 없음으로 생략되면 CPU 성능 비교 자료가 되지 않습니다.

- `thread_cpu`는 비슷하고 `wall`만 증가: CPU 할당 대기, 다른 작업과의 경쟁, I/O 대기 등 CPU를 사용하지 못하는 시간 증가를 의심합니다. 이 값만으로 CPU 제한과 I/O 대기를 확정적으로 구분할 수는 없습니다.
- `fsync`가 크게 증가: 파일 동기화 지연이 추출 시간 증가에 기여합니다. 다만 일반 읽기·쓰기와 flush 시간은 별도로 분리하지 않았습니다.
- `thread_cpu`도 크게 증가: CPU 실행 성능, 런타임, 입력 내용 차이를 추가 확인합니다.
- 동일한 원본 행 수와 바이트 수는 비교 조건 확인용이며, 내용이 완전히 동일함을 보장하지 않습니다.

진단은 파일마다 몇 차례의 시계 조회와 로그 기록만 추가하며, 행마다 로그를 출력하지 않습니다. 필터링·교체·캐시 갱신 동작은 변경하지 않았습니다.
